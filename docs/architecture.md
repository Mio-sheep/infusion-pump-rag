# 架构与设计取舍

这份文档解释代码为什么长这样。想快速上手的话看 README 就够，这里写给想改代码的人。

## 数据流

```
data/raw/*.md
   │
   │  chunker.py        拆前置元数据 → 按标题切章节 → 段落/表格切块（带重叠）
   ▼
Document(meta, chunks)  标题与正文分开存放
   │
   │  tokenizer.py      规整 Markdown → 中文取单字+二元组，拉丁文按词切
   ▼
token 序列
   │
   │  bm25.py           正文与标题分别建统计量，标题字段加权
   ▼
KnowledgeIndex ──── store.py ──── index/kb_index.json
   │                              index/kb_index.dense.json（可选）
   │
   │  retriever.py      BM25 / 稠密 / RRF 融合
   ▼
Hit[]  ──┬── generator.py   抽取式 或 大模型
         ├── cli.py
         └── server.py
```

## 为什么是 BM25 而不是向量检索打底

这类语料的查询有个很明显的特征：**用户问的是术语和编号**。
"JJF 1259"、"upstream occlusion"、"key bounce"、"VTBI"——
这些词的答案在哪里，很大程度上就是一个精确匹配问题。

BM25 在这种查询上比稠密向量强，而且强得不是一点：

- 不需要模型文件，不需要网络，clone 下来就能用；
- 罕见术语的 IDF 很高，`jjf`、`1259` 这种 token 能精确定位；
- 没有"语义漂移"——不会因为"泵"和"设备"在向量空间里接近，
  就把讲肠内营养泵的段落排在讲阻塞报警的段落前面。

稠密向量真正有用的场景是**用户不知道术语、用自己的话问**的时候，
比如问"泵一直响个不停"而不是"报警"。所以它做成了可选增强，
`hybrid` 模式下两路结果用 RRF 融合，而不是替换掉 BM25。

## 为什么融合用 RRF 而不是加权求和

BM25 的分数是无界实数（取决于查询词数和 IDF），余弦相似度在 [-1, 1]。
两者没法直接相加。

常见的做法是先各自归一化再加权，但归一化的尺度依赖当前查询的分数分布：
对某个查询，最高分 12.4、次高分 12.3，归一化后会变成 1.0 和 0.99，
差异被抹平；换个查询又反过来。

RRF（Reciprocal Rank Fusion）只看名次：

```
score(d) = Σ_r  1 / (k + rank_r(d))      k = 60
```

不需要调参，不需要知道两路分数的量纲，对某一侧偶尔抽风也更鲁棒。
代价是丢掉了分数里的"置信度"信息，但对这个规模的语料来说不值得为此增加复杂度。

## 为什么中文用字符二元组而不是分词

考虑过 jieba，最后没用的原因有三个：

1. **专业术语词典覆盖不到。** "蠕动泵""阻塞报警""不确定度"这些词，
   通用词典要么没有，要么切法不符合检索需要。
2. **会切坏单位和编号。** `mL/h`、`0.1μg/kg/min`、`IEC 60601-2-24`
   经分词器处理经常变成碎片。
3. **多一个依赖。** jieba 的词典有好几 MB，和"零依赖"的承诺冲突。

字符二元组在这些方面都是安全的：`阻塞报警` 会产出 `阻塞`、`塞报`、`报警` 三个 bigram，
任何一个都能召回；同时单字也保留，用于处理查询词的一部分出现在文档里的情况。

代价是单字带来的噪声。查询"量子色动力学"里每个字都可能在别的文档里出现，
所以分数不会严格为零。这个噪声由 IDF 压低（常用字 idf 接近 0），
实测不影响正确结果的排序 —— `tests/test_bm25.py` 里有一个用例在守着这条性质。

## 为什么出处在元数据里而不是正文里

1.0.0 的写法是每篇文档末尾一个"参考来源"小节，里面一排 Markdown 链接。
结果是：**这些链接被当成正文建索引了**。

"JJF 1259 是什么标准"这种查询，命中的第一名是某个文档的网址列表，
因为那一段里同时出现了 `JJF`、`1259`、`输液泵`、`校准规范`，关键词密度比正文还高。
1.0.0 的补救办法是按链接行占比给这类片段降权 —— 一个事后打的补丁。

1.1.0 改成：出处写进文件前置元数据，分块时剥离、不建索引，
检索时作为字段挂在结果上返回给界面和提示词。

顺带解决了两件事：正文里不再重复一遍出处（少占 token），
以及引用信息来源时不再依赖模型自己回忆。

## 为什么片段不重复写标题

1.0.0 把每个片段的文本拼成 `### 标题\n\n正文`，理由是"标题能帮助检索"。

这是对的，但用错了地方 —— 正确做法是让标题**作为独立字段**参与打分，
而不是塞进正文字符串里。塞进去有两个问题：

- 标题词的词频被算进正文，长片段里标题的影响被稀释（BM25 的长度归一化会惩罚它）；
- 正文文本里混着标题，展示和喂给模型时都要额外处理。

现在 `Chunk.heading` 是独立字段，BM25 用 `heading_weight`（默认 2.0）单独加权。

## 索引为什么拆成两个文件

`kb_index.json` 是可读的：词表、IDF、词频、片段全文、文档元数据，几百 KB，
提交进 git 之后能看出内容改了什么。

稠密向量动辄几 MB 到几十 MB，塞进同一个文件会让主索引完全失去可读性，
而绝大多数使用场景（纯 BM25）根本不需要它。所以拆到
`kb_index.dense.json`，并且 gitignore 掉 —— 它可以随时重建。

索引版本号在格式变更时递增，加载旧索引会直接报错并提示重新构建，
而不是悄悄用错的数据算出一堆看起来正常的结果。

## 评测为什么按"文档 + 小节"判定

`eval/questions.jsonl` 里每条标注写成：

```json
{"id": "q012", "question": "下游阻塞解除后有什么风险",
 "expect": [{"doc": "03-报警与故障排查", "section": "下游阻塞"}]}
```

不绑定 `chunk_id`，因为 chunk_id 由文件内序号生成，改一次
`--max-chars` 就全变了，评测集会立刻失效。小节标题是稳定的。

`section` 按子串匹配，所以写 `"阻塞"` 能同时覆盖"上游阻塞"和"下游阻塞"，
写 `"下游阻塞"` 则只匹配那一个。

指标是 Recall@1/3/5 和 MRR。没有引入 nDCG 之类的排序指标，
因为这个规模下"正确的小节有没有出现在前 3 条里"已经是足够的信号，
更细的排序质量在几十条问题上会被噪声淹没。

## 已知的局限

- **没有分页和流式输出。** 网页界面一次性返回全部结果，语料大了要改。
- **没有增量索引。** 改一个文件要全量重建。当前规模下一秒钟能跑完，
  语料上万片段时这里会先成为瓶颈（BM25 打分的实现是 O(片段数 × 查询词数)，
  没有用倒排表）。
- **BM25 参数没调过。** `k1=1.2, b=0.75` 是文献里的常见默认值，
  在这个语料上没有做过网格搜索。如果你的语料长度分布差异很大，值得试一下。
- **同义词表是手工维护的。** 覆盖了语料里实际出现的概念，不是通用词表。
  换语料要重写。
- **评测集只有几十条，且由作者自己标注。** 它足以发现明显的回归，
  不足以支撑"比某个基线好 2%"这种结论。
