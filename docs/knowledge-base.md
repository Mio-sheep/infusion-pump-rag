# 知识库的编制说明

这份文档说明 `data/raw/` 里的内容是怎么来的、依据什么标准取舍、
以及哪些地方还不能信。**如果你要拿这个知识库做任何实际判断，请先读这一页。**

## 收录范围

**收：**

- 与输液泵、注射泵直接相关的设备原理、结构、参数与失效模式；
- 临床使用中的操作规范与用药安全措施；
- 报警与故障的排查路径；
- 维护、计量校准与质量控制；
- 相关的中国标准、国际标准与监管要求（只写编号、名称与要点，不复制标准正文）。

**不收：**

- 具体患者的诊疗建议。这是给设备相关的资料，不是临床决策工具。
- 单一厂家产品的营销性描述。
- 受版权保护的付费标准原文、内部培训材料、未公开的召回调查报告全文。
- 无法追溯到任何来源的"经验之谈"。工程经验可以收，但必须标明它是经验。

## 依据等级

这是这份知识库最重要的约定。每一条结论都属于下面三档之一：

| 等级 | 含义 | 在正文里的写法 |
| --- | --- | --- |
| **A** | 标准、法规或监管机构文件明确规定 | 直接陈述，给出标准编号与条款位置，用 `[n]` 指向出处 |
| **B** | 厂家手册、权威机构指南或同行评议文献 | 陈述并标注型号/版本，或标注文献 |
| **C** | 工程惯例或作者经验判断 | **正文里明说**，例如"以下排序来自实际排查经验，标准里没有规定" |

为什么要把 C 单独标出来：这个领域里最危险的不是写错，而是**把经验包装成规范**。
"阻塞报警先查管路打折"是经验，写成"标准要求先检查管路"就是错的，
而且会让照着做的人以为有规范背书。

如果你在正文里看到一条结论既没有出处、也没有说明是经验，那是一个 bug，请提 issue。

## 出处的写法

每篇文档头部的前置元数据里列出出处，按正文引用顺序编号：

```markdown
---
title: 报警与故障排查
sources:
  - label: FDA, Examples of Reported Infusion Pump Problems
    url: https://www.fda.gov/medical-devices/infusion-pumps/examples-reported-infusion-pump-problems
  - label: IEC 60601-2-24:2012
    url: ""
---
```

正文里用 `[1]`、`[2]` 指回去。没有 URL 的出处（纸质手册、标准文本）也照写，
`url` 留空 —— 出处写清楚比给个链接更重要。

因为出处是元数据而不是正文，检索结果里也会带上它，
所以从任何一条检索结果都能知道它背后的依据是什么。

## 已知的薄弱之处

诚实地说清楚这些，比假装内容很全面有用：

1. **标准条款的引用精度有限。** 标准文本多数是付费的，正文里给出的
   条款位置来自公开的释义、目录或转述。**引用前请核对标准原文。**
   特别是标准会换版，`IEC 60601-2-24` 从第 2 版到第 3 版、
   `GB 9706.1` 从 2007 版到 2020 版，要求都有变化。

2. **具体型号的参数来自公开手册，可能不是最新版本。** 厂家会改参数、
   改报警名称、改默认值。涉及具体机型的数值，一律以你手上那台设备的
   随机说明书为准。

3. **中国医疗器械不良事件的数据很有限。** 国家药品不良反应监测中心
   公开的年度报告颗粒度较粗，输液泵/注射泵通常归在"有源医疗器械"大类里，
   拿不到按品种细分的统计。

4. **临床使用部分偏原则，缺少中国本土流程细节。** 目前的规范部分
   主要参考 FDA 与 ISMP 的材料，与国内医院的实际流程（比如查对制度的具体形式）
   有差异。如果你在一线，欢迎补充。

5. **英文文献的覆盖率高于中文文献。** 中国知网上有不少输液泵计量与
   不良事件分析的文章，但多数无法公开访问，目前只收录了少量能拿到全文的。

## 修订流程

1. 改 `data/raw/*.md`，同时更新头部的 `updated` 日期。
2. 重新构建索引：`python -m infusion_rag.cli build`。
3. 跑评测确认没有把已有的检索效果弄坏：`python -m infusion_rag.cli eval`。
4. 一起提交内容和索引。

发现内容有问题请用 [内容纠错](../../issues/new?template=content-correction.yml) 模板提 issue，
模板里会问你要依据 —— 没有依据的纠错没法判断，请理解。
