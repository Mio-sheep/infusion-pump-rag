# 检索评测

评测集在 `eval/questions.jsonl`，45 个问题，每条标注了"正确答案应该在哪个文档的哪个小节"。
复现方式：

```bash
python -m infusion_rag.cli eval --failures 10
```

## 当前结果

索引版本：`index/kb_index.json`，构建自 `data/raw/` 的 11 篇文档（81 个片段）。
检索模式 BM25，参数 `k1=1.2, b=0.75, heading_weight=2.0`。

| 指标 | 数值 |
| --- | --- |
| 问题数 | 58 |
| MRR | 0.772 |
| Recall@1 | 69.0% |
| Recall@3 | 84.5% |
| Recall@5 | 91.4% |

## 怎么理解这几个数字

**Recall@3 是最该看的那个。** 这个知识库的典型用法是"把相关段落摆出来看"，
所以前三条里有没有正确的小节，比第一条是不是正确的小节更贴近实际体验。
84.5% 意味着每 6 个问题里有 1 个要翻到第 4、5 条，或者换个问法。

**Recall@1 只有 69%，我不打算为此继续调参。** 看了失败用例之后会发现，
相当一部分"失败"其实是排序的并列问题：正确的小节排在第二，
排第一的是同一篇文档里另一个高度相关的小节，或者是一篇同样回答了这个问题的
速答文档（加入《常见问题速答》之后这类情况变多了，它是合理答案，
只是我的标注里没有把它列为可接受项）。这种情况下使用者并没有损失什么，
但指标上记为失败。继续往上调这个数字，很可能是在过拟合这 58 条标注。

**MRR 0.772** 表示平均而言正确答案出现在第 1.4 条附近。

## 判定标准为什么这样定

每条标注写成「文档 + 小节标题子串」，而不是 chunk_id：

```json
{"id":"q012","question":"阻塞报警怎么排查",
 "expect":[{"doc":"03-报警与故障排查","section":"阻塞报警"}]}
```

chunk_id 由文件内序号生成，改一次 `--max-chars` 就全部作废；
小节标题是稳定的，所以在调整分块参数的同时还能继续用同一份评测集。

代价是判定偏宽：`section` 按子串匹配，标注 `"阻塞"` 会同时接受
"上游阻塞"和"下游阻塞"两个小节。想要更严就写完整的标题。

## 已知的失败模式

看过失败用例之后，主要有三类：

1. **提问用的词和正文不一致。** 比如"额外的一次性输入"想找"阻塞解除后团注"，
   正文里用的是"团注"。同义词表能覆盖一部分，覆盖不了措辞差异大的。
2. **答案跨文档。** 比如"注射泵为什么更准"在 01 讲机理、在 02 讲低流速，
   期望里列了两个文档，但排序时第三个文档可能挤进前面。
3. **通用的铺垫段落抢排名。** "报警要分清是药的问题还是泵的问题"这一段
   和很多报警类查询都有词汇重叠，偶尔会排到具体小节前面。

三类都不是检索器的 bug，是语料本身的特性。要改善前两类，
靠的是改写正文让措辞更接近提问习惯，而不是调 BM25 参数。

## 怎么贡献标注

评测集最缺的是**不是作者本人写的问题**。作者知道答案在哪儿，
提问方式会不自觉地贴近正文的措辞，这会让分数虚高。

如果你愿意帮忙，最简单的方式是：随便问一个你真实想问的问题，
把问题和"你觉得正确答案应该在哪"发成一个 issue，
我会整理进评测集并在下一轮评测里体现。
